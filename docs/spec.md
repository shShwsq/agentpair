# AgentPair 双智能体代码安全审计系统 - 规格说明

## 1. 概述

### 1.1 产品定位
双智能体协作的代码安全审计平台,核心创新是 **user_agent 模拟用户追问** 的交互模式,在单 ReAct 架构之上叠加意图对齐与结果审视能力。

### 1.2 核心架构
```
用户输入(目的/仓库URL)
      ↓
┌─────────────┐    提问澄清     ┌──────────────┐
│ user_agent  │ ←----------→ │   用户(人)    │
│ (意图对齐+   │               └──────────────┘
│  结果审视)   │
└──────┬──────┘
       │ 定向追问请求
       ↓
┌─────────────┐
│ react_agent  │  工具调用 + 推理 + 执行
│ (ReAct 模式) │
└──────┬──────┘
       │ 执行结果
       ↓
┌─────────────┐
│ user_agent  │ 对照 checklist 评估覆盖度与深度
│ (审视+追问)  │ → 满足则输出给用户 / 不满足则继续追问 react_agent
└─────────────┘
```

### 1.3 双端策略
- **网站端**:完整功能,适合深度审计报告查看与导出
- **微信小程序端**:核心功能,适合快速扫描与移动端查看
- **后端共用**:双智能体核心逻辑作为后端服务,两端通过统一 API 访问

## 2. 场景定义

### 2.1 当前支持场景
**场景一:代码安全审计**
- 输入:GitHub 仓库 URL(可选指定分支/目录范围)
- 输出:结构化漏洞报告(CWE 分类、位置、严重度、修复建议)

### 2.2 场景扩展预留
架构上预留多场景支持(后续可加入:依赖审计、配置审计、API 设计审查等)。
用户在前端选择场景,后端按场景加载对应 checklist 与 react_agent 工具集。

## 3. 核心流程:代码安全审计

### 3.1 user_agent 阶段一:意图对齐(可选)
触发条件:用户输入模糊或缺少关键信息(如未指定分支、审计范围不清)。
- 向用户提问,**预算上限 2 轮**(避免无限澄清)
- 典型问题:
  - "请确认审计范围:全仓库还是特定目录?"
  - "是否需要检查依赖项漏洞(CVE),还是只审源码?"
  - "有特定关注的类别吗?(如认证、注入、加密)"

如果用户输入已明确,跳过此阶段直接进入 3.2。

### 3.2 react_agent 阶段:首轮扫描
user_agent 将用户意图转化为审计任务,交给 react_agent。
- react_agent 拥有工具:仓库克隆、文件读取、grep 搜索、依赖解析、可选 SAST 工具调用
- 输出首轮发现清单

### 3.3 user_agent 阶段二:对照 checklist 评估
user_agent 维护一份**漏洞类别 checklist**,每轮评估:
- 类别覆盖度:哪些类别已查、哪些未触及
- 类别深度:已查类别是否触及必查子项(见 3.4)
- 已知发现的交叉验证:是否存在相互矛盾或需要补强的结论

### 3.4 漏洞类别 checklist(基础版)
基于 OWASP Top 10 + CWE Top 25,按语言自动优先级排序。

| 类别 | 必查子项(示例) | 高风险语言 |
|------|------------------|-----------|
| 注入(SQL/Cmd/模板) | 用户输入拼接、ORM 原始查询、shell 调用 | 全部 |
| 认证与授权 | 登录流程、会话管理、IDOR、权限校验 | 全部 |
| 反序列化 | pickle/yaml/marshal/eval | Python、Java |
| SSRF | 外部 URL 请求、回调、元数据接口 | 全部 |
| 硬编码密钥 | API key、token、password、私钥 | 全部 |
| 路径穿越 | 文件操作拼接、zip 解压 | 全部 |
| 不安全加密 | 弱算法、ECB 模式、硬编码 IV | 全部 |
| XSS | 模板转义、DOM 操作、CSP | Web 应用 |
| 配置安全 | 调试模式、CORS、默认凭据 | 全部 |

> 注:此为初始 checklist,后续应按真实审计反馈持续迭代。

### 3.5 user_agent 阶段三:定向追问
当 checklist 未覆盖或深度不足时,user_agent 向 react_agent 发送**定向追问**:
- **追问要具体到类别和检查点**,禁止 "你再查查有没有别的" 这类无方向指令
- 追问要带上**已有发现作为上下文**,避免 react_agent 重复扫描
- 示例:"已发现 SQL 注入 2 处(位置见上文)。请继续检查认证与授权模块,重点关注:1) 权限校验是否在每个受保护路由上;2) JWT 验证是否校验签名与过期;3) 是否存在 IDOR(通过用户可控 ID 访问他人资源)。"

### 3.6 终止条件(硬性,避免死循环)
满足以下**全部**条件后输出最终报告:
1. checklist 所有适用类别均有明确结论(有 / 无 / 无法确定)
2. 每个类别至少触及一个必查子项
3. user_agent 追问轮次 ≤ **上限 5 轮**(可配置)
4. 最近一轮 react_agent 未产生新发现,且 user_agent 无新增追问点

## 4. 双端实现策略

### 4.1 共用后端(推荐)
- 后端服务暴露统一 REST/WebSocket API
- 核心双智能体逻辑、checklist、工具集均在后端
- 双端只负责 UI 与交互

### 4.2 前端框架选择(待定,见 8.1)
- **方案 A:网站 + 小程序分别独立开发**
  - 网站:React/Vue
  - 小程序:原生或 Taro
  - 优点:各端体验最优
  - 缺点:两套代码,维护成本高
- **方案 B:跨端框架一次开发**
  - Taro / uni-app
  - 优点:一套代码多端
  - 缺点:复杂交互在小程序端可能受限

### 4.3 长任务处理
安全审计是长任务(几分钟到几十分钟):
- **网站端**:WebSocket 实时推送进度,或轮询任务状态
- **小程序端**:异步处理,**不主动通知**,用户自行进入小程序查看进度与结果
  - 用户提交后立即返回任务 ID
  - 后端异步执行,任务列表持久化
  - 任务列表页展示状态(pending / running / completed / failed),用户过几分钟自行刷新查看
  - running 状态下可展示当前阶段(如"正在克隆仓库"、"user_agent 评估中"、"react_agent 第 3 轮扫描")
  - 前端定时轮询任务状态(建议 5-10 秒间隔,带退避)

## 5. 数据模型(核心实体)

```
Task(任务)
  - id
  - user_id
  - scenario: "code_security_audit"
  - repo_url, branch, scope
  - status: pending / running / completed / failed
  - created_at, completed_at

Conversation(对话)
  - id
  - task_id
  - role: user / user_agent / react_agent
  - content
  - type: question / answer / tool_call / tool_result / finding / followup
  - timestamp

Finding(漏洞发现)
  - id
  - task_id
  - category (CWE 类别)
  - severity: info / low / medium / high / critical
  - file_path, line_range
  - description
  - remediation
  - verified: true / false / unverified
```

## 6. 报告输出

### 6.1 报告结构
- 执行摘要(总览、严重度分布、覆盖类别)
- 漏洞清单(按严重度排序,含位置与修复建议)
- 审计覆盖说明(查了哪些类别、结论如何)
- 附录:完整对话记录(可选展开)

### 6.2 双端差异
- 网站:完整报告 + 导出 PDF/Markdown
- 小程序:精简视图(摘要 + 漏洞卡片),详细报告可跳转网页版

## 7. 安全与合规

### 7.1 仓库访问
- 仅支持公开仓库(初始版本)
- 私有仓库后续支持(需用户授权 GitHub OAuth)

### 7.2 微信内容安全
- 审计报告中可能含敏感词(如 "漏洞"、代码片段中的关键字)
- 输出前需过微信内容安全检测,避免被拦截

### 7.3 资源限制
- 单任务执行时间上限(防 react_agent 死循环)
- 单任务 token 消耗上限
- 仓库克隆大小限制

## 8. 待决策问题

### 8.1 前端框架与后端栈(已决策)
**方案:双端独立开发。**

- **网站前端**:Vue3 + TypeScript
- **小程序前端**:微信小程序原生开发
- **后端**:Python + FastAPI
- **理由**:网站要做深度报告展示与复杂交互,小程序只做核心功能与移动端查看,各自独立反而更省心,避免跨端框架的限制与调试成本

### 8.2 小程序长任务通知机制(已决策)
**方案 C:用户主动进入查看,不做主动通知。**
- 用户提交任务后立即返回任务 ID
- 用户自行进入小程序任务列表查看状态
- running 状态展示当前阶段,辅助用户判断还要等多久
- 后续如需增强体验,可考虑订阅消息作为增量功能,不作为首版必需

### 8.3 LLM 模型选择(已决策)
**方案:用户可自主配置两个 agent 用什么模型,管理员预设可选模型清单。**

- **管理员职责**:在后台配置一份「可选模型清单」(每个模型含 provider、model_name、API key、温度等参数)
- **用户职责**:在账户设置里从清单中选择 user_agent / react_agent 各自使用哪个模型
- **默认值**:管理员为两个 agent 各设一个默认模型,用户不配置时走默认
- **分离配置**:user_agent 与 react_agent 可选不同模型(react_agent 工具调用重,倾向更强模型;user_agent 偏评估与追问,可用较小模型降本)
- **支持模型源**:首版至少兼容 OpenAI 兼容接口(覆盖 OpenAI、通义千问、DeepSeek 等),后续可扩展 Anthropic 等

### 8.4 react_agent 工具集(已决策)
**首版工具集范围:**

| 工具 | 用途 | 首版 |
|------|------|------|
| clone_repo | 克隆 GitHub 仓库到沙箱 | ✓ |
| read_file / search_code | 在仓库内读文件、grep、语义搜索 | ✓ |
| run_in_sandbox | 在沙箱里执行代码(仓库代码 / agent 生成的脚本 / SAST 工具) | ✓ |
| cve_query | 解析依赖文件 + 查 CVE 数据库(OSV API) | ✓ |
| semgrep_scan | 在沙箱里跑 Semgrep 扫描仓库 | ✓ |
| skill | 调用自定义技能(见 8.6) | ✓ |

### 8.5 用户账户体系(已决策)
**方案:邮箱密码注册登录,GitHub 关联后续作为可选绑定。**

- **登录方式**:邮箱 + 密码
- **注册流程**:邮箱 + 密码 + 邮箱验证(验证后才激活账号)
- **两端统一账户**:同一套账户体系,网站和小程序共用

**密码策略(关键)**:
- **禁止「修改密码」**:登录后无法主动改密码。防止盗号者改密码锁死原主人
- **允许「重置密码」**:未登录状态下,通过邮箱验证发起重置。用户通过邮箱验证身份后设置新密码
- **系统区分**:修改密码(登录态、主动改)与重置密码(未登录、邮箱验证发起)是两个不同操作,只有后者允许

**忘记密码流程**:
1. 用户在登录页点「忘记密码」,输入注册邮箱
2. 后端发送重置链接到邮箱(链接含一次性 token,有效期 30 分钟)
3. 用户点击链接验证 token 后,设置新密码
4. 新密码生效,旧密码失效

**GitHub 关联(后续单独做,首版不实现)**:
- 作为账号设置里的可选绑定功能
- 用户在设置页绑定 GitHub(走 GitHub OAuth)
- 用途:私有仓库访问授权、关联 GitHub 身份标识、未来扩展场景
- **不作为登录方式**,登录统一走邮箱密码,避免登录入口混淆

**安全考虑**:
- 密码存储:bcrypt 加盐哈希
- 登录失败限制:同 IP 同邮箱连续失败 5 次锁定 15 分钟
- 邮箱验证 token:一次性,使用后失效
- 重置链接 token:一次性,有效期 30 分钟

### 8.6 沙箱与自定义技能机制(已决策)

**沙箱:OpenSandbox**

- 用于隔离执行不可信代码,基于 Docker 的隔离机制
- 三类执行场景:
  1. **跑仓库代码本身**:沙箱预装多语言 runtime(Python/Node/Go 等),用于跑用户仓库的测试或启动服务观察运行时行为
  2. **跑 agent 生成的验证脚本**:react_agent 写小脚本验证漏洞是否可利用(如构造 payload 测注入点),在沙箱执行取回结果
  3. **跑第三方 SAST 工具**:Semgrep 等工具在沙箱里执行扫描仓库
- 安全配置(沿用 OpenSandbox 的安全实践):
  - security_opt、资源限制(CPU/内存/执行时间)
  - 只读文件系统 + 指定可写目录
  - 网络隔离(默认无外网,需要时按需开放)
  - 执行时间硬上限(防死循环)

**自定义技能机制(SKILL)**

- **定位**:把常用的多步审计操作封装成可复用的「技能」,react_agent 按需调用
- **与普通工具的区别**:普通工具是单步操作(clone、read_file、run_in_sandbox),技能是多步编排(如「检查所有 SQL 拼接点」= grep 找拼接 + 读取上下文 + 判断是否用户可控 + 生成验证脚本)
- **技能定义格式**(初步设计):
  ```yaml
  name: check_sql_injection
  description: 检查 SQL 注入漏洞,覆盖拼接、ORM 原始查询、动态表名等模式
  steps:
    - use: search_code
      args: { pattern: "execute\\(|cursor\\.execute|\\.raw\\(", lang: auto }
    - use: read_file
      iterate_over: previous_results.matches
    - use: run_in_sandbox
      condition: needs_verification
      args: { script: "${generated_verify_script}" }
  ```
- **首版技能清单**(对应 checklist 的类别):
  - check_sql_injection(注入类)
  - check_auth_idor(认证与授权)
  - check_deserialization(反序列化)
  - check_ssrf(SSRF)
  - check_hardcoded_secrets(硬编码密钥)
  - check_path_traversal(路径穿越)
  - check_crypto_misuse(不安全加密)
- **扩展性**:管理员可后续添加新技能,用户不能自定义(避免安全风险)

### 8.7 人工审计师模式(后期功能,首版不实现)

**定位**:当用户未配置模型时,可选「人工模式」,由其他真人开发者扮演 agent 完成审计。首版不做,记录在此供后续参考。

**触发场景**:
- 用户没有配置自己的 LLM 模型(或不想消耗自己的额度)
- 用户主动选择「人工模式」,接受较长等待时间

**任务模式三选一(规划)**:
- A. 自动模式:LLM 双 agent 执行(默认)
- B. 人工模式:由真人审计师接单完成,等待时间长
- C. 混合模式(可能后期加入):LLM 先跑,真人审计师复核与补充

**激励机制:额度置换(关键设计)**

- 接单帮别人审计 → 获得额度
- 额度可用于:调用管理员预置的 LLM 模型跑自己的任务
- 形成正向循环:帮别人审 → 赚额度 → 自己任务用 LLM 跑
- 管理员预置模型作为公共资源池,所有用户共享
- 不涉及真实金钱流动(避免支付合规与微信虚拟支付管控问题)

**防滥用**:
- 单次接单获得的额度有上限
- 接单质量评估机制(提问者评分)
- 接单后未完成的惩罚(扣额度或限制接单)
- 管理员预置模型的总消耗成本需可控(避免一人帮审水任务换大量 LLM 调用)

**关键设计问题(待后续细化)**:
- 供需匹配机制:谁接哪个任务?先到先得 vs 匹配?
- 隐私:用户提交的代码愿意让其他用户看吗?是否需要遮蔽敏感信息?
- 质量:真人水平参差,如何保证审计质量?
- 责任:漏报出事谁负责?
- 任务超时:接单后多久未完成算放弃?

**前置条件**:
- 用户量达到一定规模(冷启动期人工池为空,功能无意义)
- 双 LLM agent 模式已稳定运行,有对比基线
